# Yudao 部署及排错记录

在配置和使用 Docker 部署 `yudao-ui-admin-vue3` 项目的过程中，我们遇到了一系列环境、依赖和代码层面的问题。为避免后续重复踩坑，特将这些问题及相应的解决方案整理在此。

## 1. 页面白屏报错：`ReferenceError: im is not defined`
* **现象**：本地运行或部署后打开页面，显示一片空白，浏览器控制台抛出 `im is not defined` 的红色错误。
* **原因**：项目中集成了即时通讯 (IM) 组件（位于 `src/layout/components/ToolHeader.vue` 中），但由于当前环境未包含或未正确注册 IM 相关的数据结构，导致 Vue 在解析模板时找不到对应变量直接崩溃。
* **解决方案**：确认当前业务场景暂不需要 IM 功能后，直接在 `ToolHeader.vue` 中注释掉了所有 `im` 相关的变量定义、DOM 节点显示以及 `@click="goToChat"` 的点击事件绑定。

## 2. Windows 批处理脚本 (.bat) 编码与换行符问题
* **现象**：编写 `deploy.bat` 一键部署脚本时，双击运行报错或出现乱码。
* **原因**：Windows 系统的 `cmd` 终端对批处理脚本的编码（通常需要 ANSI/GBK/Default）和换行符（严格要求 CRLF）非常敏感。如果是 UTF-8 且为 LF 换行，极易报错。
* **解决方案**：确保新建的 `deploy.bat` 脚本使用了当前系统兼容的默认编码，并将换行符强行转存为了 `CRLF`。

## 3. 路由 History 模式导致 Docker 内 404
* **现象**：将 `dist` 放入 Nginx 镜像后，访问首页正常，但手动刷新带有具体路径的页面会导致 404 Not Found。
* **原因**：Vue Router 启用了 History 模式，所有的子路径都会被 Nginx 当作真实的物理文件夹去查找，找不到就会 404。
* **解决方案**：在项目根目录新增了 `nginx.conf` 配置文件，并在 `Dockerfile` 中替换掉了容器内的默认配置，加入了关键配置：`try_files $uri $uri/ /index.html;` 来实现路由后备回退。

## 4. `pnpm build` 报错 `MODULE_NOT_FOUND` (写死绝对路径)
* **现象**：执行打包命令时提示找不到 `./node_modules/vite/bin/vite.js`。
* **原因**：原项目的 `package.json` 中，将 `build:prod` 脚本写死成了 `node --max_old_space_size=8192 ./node_modules/vite/bin/vite.js build --mode prod`。由于 `pnpm` 采用了符号链接（symlink）的虚拟存储机制，直接去寻找此固定路径非常容易导致找不到文件。
* **解决方案**：修改 `package.json` 中的 `scripts`，将写死的路径统一替换为包管理器标准的唤起方式：`vite build --mode prod`，让 pnpm 自动解析程序路径。

## 5. `pnpm install` 异常导致 `vite` 命令丢失
* **现象**：修改完上述问题后，打包时又提示 `'vite' 不是内部或外部命令`。
* **原因**：由于历史安装操作、pnpm 版本变更等原因，当前的 `node_modules` 文件夹底层软链结构已经损坏（触发了 `ERR_PNPM_VIRTUAL_STORE_DIR_MAX_LENGTH_DIFF` 错误），导致 `pnpm` 拒绝为新包生成 `.bin` 目录下的可执行文件映射。
* **解决方案**：使出终极必杀技：彻底删除已损坏的 `node_modules` 文件夹，然后重新执行了一次纯净的 `pnpm install`。

## 6. pnpm 严格模式拦截底层依赖编译 (Postinstall 拦截)
* **现象**：执行 `pnpm install` 时，控制台打印警告 `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild...`，随之而来的是打包再度因为缺少 `esbuild` 核心二进制库而失败。
* **原因**：高版本（>= 9.0）的 `pnpm` 出于安全考虑，默认拦截所有依赖包自带的自动化编译脚本。如果不允许 `esbuild` 运行其脚本，它就不会去下载底层的 `.exe` 打包组件，导致前端构建瘫痪。
* **解决方案**：执行 `pnpm approve-builds` 命令，在交互式菜单中全选（`esbuild`, `@parcel/watcher` 等），将它们加入到了 `package.json` 的白名单配置中，最后重新 `pnpm install`，彻底打通了部署链路。

## 7. 后端 AI 模块启动报错 `NoClassDefFoundError: TextToSpeechModel`
* **现象**：后端 `yudao-server` 编译成功，但启动时在实例化 `DashScopeAudioSpeechAutoConfiguration` 时抛出类找不到异常。
* **原因**：虽然在 `yudao-module-ai-server` 中指定了 `spring-ai.version` 为 `1.1.8`，但由于全局引入了 `spring-cloud-alibaba-dependencies`，它在底层通过 `dependencyManagement` 将 `spring-ai-core` 等依赖强行隐式降级到了 `1.0.2` 版本。而旧版本中不存在 `TextToSpeechModel` 类，导致运行时因版本不匹配报错。
* **解决方案**：在根目录的 `yudao-dependencies/pom.xml` 全局依赖管理中，显式加入 `spring-ai-bom` 并锁死版本为 `1.1.8`。这强制阻断了 Spring Cloud Alibaba 等其他 BOM 对 AI 核心包的降级行为。

## 8. 后端 AI 模块启动报错 `ChatClientAutoConfiguration required a single bean, but 12 were found`
* **现象**：解决依赖版本后，`yudao-server` 启动再次崩溃，提示 Spring 容器中找到了 12 个 `ChatModel` 类型的 Bean，导致 `ChatClientAutoConfiguration` 无法完成自动装配。
* **原因**：Spring AI 的 `ChatClientAutoConfiguration` 设计初衷是给“单模型项目”用的，它会去寻找唯一的 `ChatModel` 来创建一个全局通用的 `ChatClient.Builder`。然而，在 Yudao 的多模型架构中（`AiAutoConfiguration`），一次性注册了 OpenAI、DashScope、DouBao 等 12 种不同的模型客户端供系统动态调度。由于目标不唯一，导致自动装配彻底崩溃。
* **解决方案**：Yudao 底层使用的是自带的 `AiModelFactory` 进行多模型动态精准调度，完全不需要 Spring AI 提供的单模型泛用构建器。在 `YudaoServerApplication` 启动类上的 `@SpringBootApplication` 注解中，通过 `excludeName` 属性直接排除了 `org.springframework.ai.model.chat.client.autoconfigure.ChatClientAutoConfiguration`，阻断了其无意义的自动装配。

## 9. 前端 Vite 打包报 `[lightningcss minify] Unexpected token Semicolon` (`*zoom: 1;`)
* **现象**：执行 `npm run build:prod` 打包前端时，Vite 报错 `[lightningcss minify] Unexpected token Semicolon`，定位在 `*zoom: 1;` 处构建中断。
* **原因**：前端部分老旧样式文件（如 `.clearfix`）包含 IE6/7 专用的 CSS Hack（`*zoom: 1;`），而现代化构建工具 Vite 使用基于 Rust 的新一代超快 CSS 压缩引擎 `lightningcss`，严格遵循现代标准，无法兼容解析带有非法星号前缀的属性，直接抛出语法异常。
* **解决方案**：在源码样式中排查并清除过时的 IE Hack 属性（删除 `*zoom: 1;`），恢复标准的现代清除浮动写法。

## 10. 前端 Docker 构建提示找不到 `dist` 目录 (`stat dist: file does not exist`)
* **现象**：前端编译成功后构建 Docker 镜像时报错 `COPY failed: stat dist: file does not exist`。
* **原因**：原前端 `package.json` 的生产打包命令 `npm run build:prod` 默认输出目录为 `dist-prod`，而不是常规的 `dist`。而前端的 `Dockerfile` 固定写死 `COPY dist /usr/share/nginx/html/`，导致找不到产物目录。
* **解决方案**：在前端自动化脚本 `docker/frontend/build.bat` 中加入产物自动识别与同步逻辑，优先检测 `dist-prod` 目录，若存在则自动拷贝同步为 `docker/frontend/dist`，无需修改已有 Dockerfile。

## 11. Windows 批处理脚本 (.bat) 复合括号陷阱导致“无声瞬间闪退”
* **现象**：双击运行 `build.bat` 或 `start.bat` 时，黑框窗口一闪而过立刻关闭，无任何报错提示；甚至首行 `echo` 都没有打印出来。
* **原因**：
  1. **复合括号语法截断（致命）**：Windows `cmd.exe` 解释器在解析 `if (...)`、`for (...)` 复合多行语句块时，如果内部代码包含半角圆括号 `( )`（例如 `echo [1] 使用现有包 (推荐)`、注释中的括号、或环境变量展开后带括号），CMD 会将第一个出现的闭括号 `)` 错误当成整个语句块的结束符，导致语法解析崩溃并在启动前瞬间退出。
  2. **换行符不匹配**：脚本若被 Git 或跨平台编辑器保存为 Linux 的 `LF` 换行符，CMD 无法稳定识别换行，极易触发解析混乱闪退。
* **解决方案**：
  1. 彻底弃用复杂的嵌套 `if (...) else (...)` 复合块，改用全线性的**标签与 `goto` 跳转**结构（扁平化执行流）。
  2. 强制将所有 `.bat` 脚本转换为 Windows 专属的 **CRLF (`\r\n`)** 换行符，并在 `docker/.gitattributes` 中配置 `*.bat text eol=crlf` 锁定。
  3. 在脚本关键错误分支和退出点统一增加清晰的错误 `echo` 和 `pause` 命令，确保即使出错也保持窗口常驻供开发者查看原因。

## 12. Windows 批处理脚本控制台中文输出乱码
* **现象**：运行批处理脚本时，控制台中文变成乱码（如 `[MES 閮ㄧ讲宸ュ叿] 姝ｅ湪寮€濮?...`）。
* **原因**：Windows CMD 默认代码页为 GBK（代码页 936），而项目中的批处理脚本采用 UTF-8 编码保存。GBK 终端直接解析 UTF-8 的中文字符流会发生解码错位。
* **解决方案**：在所有批处理脚本（`start.bat`、`stop.bat`、`build.bat`）的开头第一行统一添加：
  ```bat
  chcp 65001 >nul
  ```
  强制将当前 CMD 窗口的代码页切换为 UTF-8（65001），并使用 `>nul` 屏蔽系统切换提示，彻底解决中文乱码。

## 13. 本地宿主机 MySQL 3306 端口冲突与容器内外网络隔离偏差
* **现象**：启动 `docker-compose` 时报错：
  `Ports are not available: listen tcp 0.0.0.0:3306: bind: Only one usage of each socket address is normally permitted.`
* **原因**：本地 Windows 电脑安装有原生 MySQL 服务并开机自启，占用了宿主机的 `3306` 端口，导致 Docker 无法将容器端口绑定到宿主机的 3306。
* **解决方案与核心认知**：
  1. 将 `docker/.env` 中的宿主机映射端口 `MYSQL_PORT` 修改为 **`3307`**（即 `3307:3306`）。
  2. **容器内外网络隔离避坑认知**：
     - **宿主机外部访问**：开发者使用 Navicat / DBeaver 从宿主机电脑连接 Docker 里的数据库时，主机填 `localhost`，端口填写映射出来的 **`3307`**。
     - **容器内部网络访问**：在 Docker 桥接网络（`mes-net`）中，后端容器 `mes-backend` 访问 `mes-mysql` 时，走的是容器内部虚拟网络，端口依然是 **`3306`**，JDBC URL 必须维持为 `jdbc:mysql://mes-mysql:3306/ruoyi-vue-pro`，**绝对不能**改成 3307！

## 14. Spring Boot 单体聚合打包子模块未跳过 repackage 导致 Bean 丢失 (`ApiErrorLogCommonApi`)
* **现象**：Docker 后端容器启动时报严重错误崩溃：
  ```text
  Parameter 0 of method globalExceptionHandler in cn.iocoder.yudao.framework.web.config.YudaoWebAutoConfiguration
  required a bean of type 'cn.iocoder.yudao.framework.common.biz.infra.logger.ApiErrorLogCommonApi' that could not be found.
  ```
* **原因**：
  1. 本项目采用单体架构部署，由 `yudao-server` 聚合各业务子模块（`infra`、`system`、`mes`、`bpm` 等）。
  2. 子模块（如 `yudao-module-infra-server`、`yudao-module-system-server`）的 `pom.xml` 中配置了 `spring-boot-maven-plugin:repackage` 且**未加 `<skip>true</skip>`**。
  3. Maven 在构建子模块时，将其打成了 Spring Boot 可执行胖包（所有 class 文件被移动到了内部的 `BOOT-INF/classes/` 目录中）。
  4. 当外层主单体模块 `yudao-server` 依赖这些子模块并打入主包时，这些胖包被放到了主包的 `BOOT-INF/lib/` 下。Spring Boot 的 `LaunchedURLClassLoader` 在加载依赖 jar 时**只扫描根目录，根本无法穿透扫描依赖包内部的 `BOOT-INF/classes/`**！
  5. 导致 `ApiErrorLogApiImpl` 及其它 Service/Controller 变成“隐形类”，Spring 上下文扫描完全找不到 Bean，导致依赖注入失败。
* **解决方案**：
  在所有被 `yudao-server` 聚合的子模块 `*-server/pom.xml` 中，给 `spring-boot-maven-plugin` 显式配置 `<skip>true</skip>`：
  ```xml
  <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <configuration>
          <skip>true</skip>
      </configuration>
  </plugin>
  ```
  保证子模块输出标准的普通类库 Jar 包（类位于根路径），仅保留主启动模块 `yudao-server` 执行 `repackage`。

## 15. 构建脚本静默复用已损坏的旧 Jar 包陷阱
* **现象**：在修复了代码或 POM 配置后，重新运行构建脚本并启动容器，报错依旧原样复现，仿佛代码修改完全没有生效。
* **原因**：构建脚本为了提速，如果检测到本地已存在旧的 `yudao-server.jar`，如果用户直接按回车，或者脚本在未检测到 `mvn` 时自动静默回退降级，就会一直复用数天前打包的损坏旧包（9月9日产物），掩盖真实修复结果。
* **解决方案**：重构 `docker/backend/build.bat` 脚本：
  1. 提供显式的控制台选择菜单：`[1] 复用现有包 / [2] 重新执行完整 Maven 编译打包`。
  2. 若用户选择重新编译（或传入 `-r / --rebuild`），严禁静默回退，遇到环境问题必须直接阻断报错并提示原因。

## 16. Windows 环境下 Maven 与 JDK 工具链识别受阻
* **现象**：本地已安装 Maven 和 JDK，但在批处理脚本中执行 `where mvn` 提示找不到命令。
* **原因**：Windows 系统环境变量 `PATH` 中引用的 `%MAVEN_HOME%\bin` 在嵌套批处理执行环境中不会自动递归展开，或者变量仅配置在当前登录用户的用户变量域中。
* **解决方案**：在 `docker/backend/build.bat` 中增加自愈探测机制：
  1. 优先查当前会话 `where mvn`；
  2. 若未找到，主动从注册表 `HKLM`（系统级）与 `HKCU`（用户级）查询 `MAVEN_HOME` 与 `JAVA_HOME`；
  3. 探测常见磁盘路径（如 `D:\maven\...`、`D:\java\jdk-17...`），检测到后动态注入到当前会话的 `PATH`，保证打包命令开箱即用。

## 17. Maven 打包报 testCompile 编译错误（`-DskipTests` 与 `-Dmaven.test.skip=true` 差异）
* **现象 1（编译错误）**：执行 Maven 打包时，报错中断：
  ```text
  [ERROR] Failed to execute goal org.apache.maven.plugins:maven-compiler-plugin:3.14.0:testCompile (default-testCompile) on project yudao-module-report-server: Compilation failure:
  [ERROR] GoViewDataServiceImplTest.java:[3,47] 程序包cn.iocoder.yudao.framework.test.core.ut不存在
  ```
* **现象 2（版本丢失错误）**：若手动解开 `pom.xml` 中 `yudao-spring-boot-starter-test` 注释，Maven 会直接报 POM 解析异常：
  ```text
  [ERROR] 'dependencies.dependency.version' for cn.iocoder.cloud:yudao-spring-boot-starter-test:jar is missing.
  ```
* **原因**：
  1. **测试组件未纳入管理**：本分支移除了测试模块 `yudao-spring-boot-starter-test`，且在根依赖 BOM（`yudao-dependencies/pom.xml`）中没有该项的管理版本，因此不能在 POM 中直接声明该依赖（否则报 version missing）。各业务子模块（`mes`、`bpm`、`pms`、`ai`、`report`）均统一将其注释。
  2. **Maven 跳过测试参数认知陷阱（核心）**：
     - **`-DskipTests`**：仅跳过单测**运行**，**仍会编译** `src/test/java` 下的测试用例！由于没有测试依赖，`testCompile` 阶段必然直接报错崩溃。
     - **`-Dmaven.test.skip=true`**：不仅跳过测试运行，且**彻底跳过测试代码的编译**（不会生成 `test-classes`）。
* **解决方案**：
  1. 保持各子模块对 `yudao-spring-boot-starter-test` 的注释状态不变。
  2. 构建打包命令统一且必须使用 **`-Dmaven.test.skip=true`**：
     ```bash
     mvn clean package -Dmaven.test.skip=true -pl yudao-server -am
     ```
     已在 [docker/backend/build.bat](file:///d:/mes/mes/docker/backend/build.bat) 和 [docker/backend/build.sh](file:///d:/mes/mes/docker/backend/build.sh) 中完成更新。

## 18. Docker Redis 未设密码时传入空字符串导致 Redisson 鉴权崩溃 (`ERR AUTH called without any password`)
* **现象**：后端服务启动时在创建 `OAuth2AccessTokenRedisDAO` 或 `OAuth2TokenServiceImpl` 时报依赖注入失败：
  ```text
  Caused by: org.redisson.client.RedisException: ERR AUTH <password> called without any password configured for the default user. Are you sure your configuration is correct?
  ```
* **原因**：
  1. 项目自带的 `docker/redis/conf/redis.conf` 未配置 `requirepass`，即 Redis 运行在无密码模式下。
  2. 在 `docker-compose.yml` 中配置了环境变量 `SPRING_DATA_REDIS_PASSWORD: "${REDIS_PASSWORD}"`。当 `.env` 中 `REDIS_PASSWORD` 为空时，Docker Compose 会给容器注入空字符串 `""`（非 null）。
  3. Spring Boot 的 Redisson 客户端检测到配置中的 password 不为 null，便在建立连接时主动向 Redis 节点发送了 `AUTH ""` 空密码认证请求。
  4. Redis 7.x 发现客户端尝试对一个无密码的 Redis 执行 AUTH 指令，直接抛出 `ERR AUTH called without any password configured` 异常，导致 `StringRedisTemplate` 及其上层业务 DAO 无法创建。
* **解决方案**：
  在 `docker/docker-compose.yml` 中，如果 Redis 未配置 `requirepass`，移除向后端注入的 `SPRING_DATA_REDIS_PASSWORD` 环境变量，使 Spring Boot 采用默认的 null 密码配置，直连 Redis 建立会话。

## 19. Flowable 引擎启动报主键冲突异常 (`Duplicate entry 'eventregistry.schema.version' for key 'act_ge_property.PRIMARY'`)
* **现象**：后端服务启动时在初始化 Flowable 工作流引擎 `ProcessEngineFactoryBean` 时抛出 SQL 完整性约束异常并崩溃：
  ```text
  Caused by: java.sql.SQLIntegrityConstraintViolationException: Duplicate entry 'eventregistry.schema.version' for key 'act_ge_property.PRIMARY'
  ```
* **原因**：
  在初始化数据库时已经导入了 RuoYi-Vue-Pro 全量 SQL（其中已包含完整的 `ACT_*` 工作流表结构与默认系统属性）。而 Spring Boot 中默认配置为 `flowable.database-schema-update: true`，每次启动时 Flowable 引擎都会试图重新执行一次建表脚本中的 `insert into ACT_GE_PROPERTY values ('eventregistry.schema.version', ...)` 插入指令，从而触发主键重复冲突。
* **解决方案**：
  在 `docker/docker-compose.yml` 中为后端服务增加环境变量：
  ```yaml
  FLOWABLE_DATABASE_SCHEMA_UPDATE: "false"
  ```
  关闭 Flowable 启动时的 DDL 重复初始化与默认数据插入，直接复用已导入的现有表结构。

## 20. Windows 下通过管道导出/导入 SQL 导致编码错乱与单引号被转义 (`ERROR 1064: You have an error in your SQL syntax near '鍒涘缓鑰?...'`)
* **现象**：
  启动 `mes-mysql` 容器后，进入容器查询数据表数量只有 38 张（全为 `act_*`、`flw_*` 等工作流表），所有业务表（`system_*`、`infra_*`、`mes_*` 等 300 多张表）均未生成。查看容器初始化日志发现执行 SQL 中断报错：
  ```text
  ERROR 1064 (42000) at line 1610: You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '鍒涘缓鑰?...'
  ```
* **原因**：
  1. 在 Windows 环境（PowerShell / CMD）中执行 `mysqldump ... > init.sql` 管道重定向时，Windows 控制台默认代码页（如 GBK / CP936）或 PowerShell 管道字符流会对多字节 UTF-8 编码进行二次重编码与换行截断，导致 SQL 脚本中的中文注释（如字段说明“创建者”）被破坏为乱码。
  2. 乱码截断后，某些中文字符的末尾字节恰好变成了 ASCII `0x5C`（反斜杠 `\`），导致 SQL 注释后的闭合单引号 `'` 被反斜杠转义（`\'`），MySQL 词法解析器无法找到注释闭合符，直接在第 1610 行抛出 SQL 语法错误，后续 300 多张业务表 DDL 与全量数据插入被完全阻断。
* **解决方案**：
  1. **导出时**：禁止在 Windows 终端使用 `>` 标准输出重定向导出 SQL！必须使用 `mysqldump` 原生 `-r`（或 `--result-file`）参数直接写入文件，并强制指定 `utf8mb4`：
     ```bash
     mysqldump -h 127.0.0.1 -P 3306 -u root -p --default-character-set=utf8mb4 --hex-blob --databases ruoyi-vue-pro -r "docker/mysql/init/01-ruoyi-vue-pro.sql"
     ```
  2. **导入时**：在 Windows 下向 Docker 容器导入大体积 SQL 时，避免经由 PowerShell 字符管道，采用 CMD 原始重定向：
     ```bash
     cmd /c "docker exec -i mes-mysql mysql -uroot -p123456 --default-character-set=utf8mb4 ruoyi-vue-pro < docker/mysql/init/01-ruoyi-vue-pro.sql"
     ```

## 21. 【大屏设计器】页面嵌入报 `127.0.0.1 拒绝连接` (GoView 独立前端未运行)
* **现象**：
  进入管理后台【报表管理】 $\rightarrow$ 【大屏设计器】时，页面 Iframe 区域报错：`127.0.0.1 拒绝连接。 (ERR_CONNECTION_REFUSED)`。
* **原因**：
  1. 与【报表设计器】、【仪表盘设计器】（底层基于积木报表 JimuReport，直接内嵌在 Spring Boot 后端 Jar 包中）不同，【大屏设计器】采用的是第三方独立的低代码大屏开源项目 **GoView**（基于 Vue3 + NaiveUI + ECharts5）。
  2. 管理后台前端 [`yudao-ui-admin-vue3/src/views/report/goview/index.vue`](file:///d:/mes/mes/yudao-ui/yudao-ui-admin-vue3/src/views/report/goview/index.vue) 通过 `<iframe>` 嵌入外部页面，地址读取环境变量 `VITE_GOVIEW_URL`（默认为 `http://127.0.0.1:3000`）。
  3. GoView 属于独立前端项目，并未包含在基础的 MES 前端构建物中，默认 Docker 容器编排中也没有运行 GoView 容器。由于当前宿主机没有监听 3000 端口，浏览器发起请求必然被拒绝。
* **解决方案**：
  1. **本地开发调试**：
     克隆官方适配前端仓库并启动独立前端服务：
     ```bash
     git clone https://gitee.com/zhijiantianya/yudao-ui-go-view.git
     cd yudao-ui-go-view
     pnpm install && pnpm dev
     ```
     启动后监听在 `http://localhost:3000`，刷新 MES 后台即可无缝单点登录进入设计器。
  2. **生产容器化部署**：
     在 `yudao-ui-go-view` 执行 `pnpm build`，将其静态文件集成至 `mes-frontend` Nginx 的 `/goview/` 路径，或在 `docker-compose.yml` 中新增独立的 `mes-goview` 容器。
  3. **暂不使用**：
     可在【系统管理】 $\rightarrow$ 【菜单管理】中将“大屏设计器”菜单隐藏或停用，对 MES 核心业务零影响。
  > 详细的技术架构、SSO 认证流转、数据表 DDL 与生产容器化方案已沉淀至独立专题文档：[docs/大屏设计器(GoView)开发与部署指南.md](file:///d:/mes/mes/docs/大屏设计器(GoView)开发与部署指南.md)。
