## 一、 为什么前次裁剪“效果不理想”？深度根因剖析 (Post-Mortem)

在 2026 年 9 月 15 日，团队曾编写过《Yudao Admin Uniapp 模块裁撤与架构对齐设计文档》，但在后续实际推进中，开发人员与车间现场反馈“效果很不理想”，甚至出现了移动端代码无法提交、IDE 卡死、菜单死链频出的情况。

经本次深度排查，穿透出前次不理想的 **四大致命工程软肋**：

```
[病灶 1: 纸面设计未物理闭环] ➔ 仅形成了设计文档或局部注释，未执行底层物理彻底清除，重新引入模板后全量回潮
[病灶 2: Git 规则缺失导致 42 万文件雪崩] ➔ 根与子项目缺 .gitignore，依赖库 423,897 个文件淹没版本控制，IDE 彻底卡死
[病灶 3: IDEA VCS 映射盲区] ➔ .idea/vcs.xml 误配独立子仓库，导致移动端代码变动在 IDEA Commit 窗口彻底“隐形”
[病灶 4: 静态隐式依赖产生悬空报错] ➔ 删了枚举但 constants.ts 仍 re-export，删了页面但 BPM 跳转映射产生死链
```

### 1. 纸面设计 vs 物理未闭环
- **前次教训**：上次改造更多停留在文档规划和部分配置文件的注释，没有下重手对物理目录执行“彻底物理删除”；当再次重新引入或拉取模板时，数万行无用代码再次全量覆盖回潮。
- **本次纠偏**：**先删物理目录，再做语法解耦**。对 9 大无关业务包、9 大 API 目录、7 大统计模块执行硬删除，不留任何死灰复燃空间。

### 2. Git 规则漏洞导致 42.4 万个文件雪崩
- **前次教训**：移动端子工程目录下**没有任何 `.gitignore`**，且项目根目录 `.gitignore` 也仅有 Java/Maven 规则，完全漏掉了前端通用的 `node_modules`。
- **破坏后果**：一旦在移动端执行 `pnpm install`，瞬间生成 **423,897 个依赖小文件**，IDE 的 Git 插件疯狂递归扫描，显示“未进行版本管理的文件 424,712 个，正在更新...”，导致代码提交功能彻底瘫痪，开发人员甚至不敢打开 Git 窗口。
- **本次纠偏**：在根目录与移动端子目录下构建多层防腐 `.gitignore`，不仅屏蔽 `node_modules`，更把 `.pnpm-store/`、`dist/`、`dist-*/`、`unpackage/` 等一网打尽。

### 3. IDEA 的 VCS 映射隐形陷阱
- **前次教训**：在 `.idea/vcs.xml` 中，之前残留了一行配置：`<mapping directory="$PROJECT_DIR$/yudao-ui/yudao-ui-admin-uniapp" vcs="Git" />`。
- **破坏后果**：IDEA 将其当成一个独立的 Git 子仓库，但该目录下实际根本没有独立的 `.git` 文件夹！导致主项目的 Commit 提交窗口认为该目录由子仓库负责而不予扫描，子仓库又失效，最终**开发者在 IDEA 里修改了任何移动端代码，在 IDEA 的 Commit 变更树里都完全看不见，误以为改动丢失或未纳入版本控制**。
- **本次纠偏**：彻底清除多余的子映射，让主项目的根 Git 统一纳管。

### 4. 静态交叉引用治理不彻底
- **前次教训**：只删了部分文件，未做全局静态引用扫描。例如 `src/utils/constants.ts` 还在 `export * from './constants/biz-erp-enum'`，导致项目随时可能因找不到模块而构建报错。
- **本次纠偏**：执行全项目静态依赖扫描，清理导出，注释 BPM 表单跨分包死链。

## 二、 移动端现场定位与模块裁撤矩阵

针对伺服电机与模组的现场装配、车间 PDA 扫码、工位工控机报工的实操环境，我们将移动端功能收敛至以下纯净边界：

| 模块名称 | 对应目录 | 最终处理 | 现场场景与判定理由 |
| :--- | :--- | :---: | :--- |
| **MES 制造执行** | `src/pages-mes/`, `src/api/mes/` | ✅ **核心保留** | 车间命脉：工序路线、工位扫码报工、安灯呼叫、质检放行、设备点检维保 |
| **WMS 仓储物流** | `src/pages-wms/`, `src/api/wms/` | ✅ **核心保留** | 仓储命脉：四级仓位码扫描、原料出库、完工入库、移库调拨、动态盘点 |
| **BPM 工业流程** | `src/pages-bpm/`, `src/api/bpm/` | ✅ **核心保留** | 现场异常流程协同：物料超领审批、工单变更、MRB 不良品评审处置 |
| **AI 工业助手** | `src/pages-ai/`, `src/api/ai/` | ✅ **核心保留** | 现场技术支持：伺服排障知识库问答、排产异常预测 Copilot |

| **System 系统中心**| `src/pages-system/`, `src/api/system/`| ✅ **基础保留** | 操作工登录、个人中心、修改密码、通知公告 |
| **Infra 基础设置** | `src/pages-infra/`, `src/api/infra/` | ✅ **基础保留** | 移动端运行配置与定时任务状态监控 |
| **MP 公众号服务** | `src/pages-mp/`, `src/api/mp/` | ✅ **基础保留** | 微信模板消息与移动端服务通道 |

## 三、 四大关键治理动作与技术落地

### 1. 物理清除 9 大冗余业务模块
通过脚本进行底层强力清除（带只读属性强制解锁与子目录递归删除）：
- 物理删除分包：`pages-crm`、`pages-erp`、`pages-fms`、`pages-hrm`、`pages-im`、`pages-iot`、`pages-mall`、`pages-member`、`pages-pay`；
- 物理删除接口：`api/crm`、`api/erp`、`api/fms`、`api/hrm`、`api/im`、`api/iot`、`api/mall`、`api/member`、`api/pay`；
- 物理删除统计：`pages-statistics/` 下的 `crm`、`erp`、`fms`、`hrm`、`im`、`iot`、`mall`；
- 物理删除常量：`biz-crm-enum.ts`、`biz-erp-enum.ts`、`biz-fms-enum.ts`、`biz-im-enum.ts`、`biz-iot-enum.ts`、`biz-mall-enum.ts`、`biz-pay-enum.ts`。

### 2. 构建与分包解耦（`vite.config.ts`）
在 `subPackages` 中将已删除的分包以单行注释化保留，清理 `UniKuRoot.excludePages` 中的悬空路径，既保障 Vite 编译不扫描死目录，又保留未来工程参考标记。

### 3. 工作台菜单“零侵入黑名单过滤”（`src/pages/index/index.ts`）
- **绝不篡改原始 `menu.json`**：避免因手改庞大 JSON 文件引发语法错误或阻碍未来菜单增量升级；
- **在菜单加载层注入动态黑名单**：
  ```ts
  const DISABLED_MODULE_KEYS = [
    'crm', 'erp', 'fms', 'hrm', 'im', 'iot', 'mall', 'member', 'pay'
  ]
  ```
- **自动向下传导过滤**：在 `getMenuGroups()` 时直接过滤掉非制造分组，使搜索池、常用菜单、工作台列表同步剔除死链，工人打开工作台只能看到 MES、WMS、流程审批、AI 助手与系统设置。

### 4. Git 治理与 IDEA VCS 映射修正
- **根目录 [.gitignore](file:///d:/mes/mes/.gitignore)** 补充全局规则：
  ```gitignore
  node_modules/
  **/node_modules/
  .pnpm-store/
  **/.pnpm-store/
  dist/
  **/dist/
  dist-*/
  **/dist-*/
  unpackage/
  **/unpackage/
  .eslintcache
  pnpm-debug.log*
  yarn-error.log*
  npm-debug.log*
  ```
- **移动端子目录 [yudao-ui/yudao-ui-admin-uniapp/.gitignore](file:///d:/mes/mes/yudao-ui/yudao-ui-admin-uniapp/.gitignore)** 新建专属规则；
- **修正 [.idea/vcs.xml](file:///d:/mes/mes/.idea/vcs.xml)**：彻底删除 `yudao-ui-admin-uniapp` 独立的错误映射，彻底解决 IDEA Commit 窗口无法识别移动端改动的问题。

## 四、 防复发标准化流程（FDE 脚手架军规）

为了避免后续因项目重构、升级拉取代码再次导致“42 万文件雪崩”或“冗余模块回潮”，确立以下 **三条刚性军规**：

1. **先查 `.gitignore`，再跑 `pnpm install`**：
   引入任何新的前端或移动端子工程时，第一步必须检查是否具备独立的 `.gitignore` 且根目录是否覆盖了 `node_modules`，严禁让几十万个第三方依赖包裸奔进入版本控制。
2. **拒绝单一多仓库映射（Mono-Repo VCS 单一真实源）**：
   除非子项目自身有独立的远程 Git 仓库（Submodule），否则严禁在 `.idea/vcs.xml` 中手工添加子目录映射，必须统一由项目根目录 `$PROJECT_DIR$` 的 Git 全局接管。
3. **裁撤执行“三件套闭环”**：
   任何业务模块的裁剪，必须同时闭环：**① 物理删除目录 ➔ ② 构建配置注销 ➔ ③ 静态导出与工作台菜单过滤**，杜绝“只做一半”的半吊子重构。
